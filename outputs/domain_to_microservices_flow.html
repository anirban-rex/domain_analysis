Architecture plan · proposed workflow

From signals to domains to microservices

A staged workflow for extracting relationship-level evidence, using a weighted class graph and Louvain to propose candidate domains, validating those boundaries, and only later extracting suitable modules as microservices.

Important distinction: a Louvain community is a candidate domain, not automatically a deployable microservice. Cross-community calls are coupling to analyze—not edges to blindly delete or convert to REST.

Evidence used to build the graph

Use pairwise evidence to create cohesion edges. Preserve directed dependencies separately so interaction is not confused with ownership.

Availability-aware affinity

Aᵢⱼ = Σₖ αₖ mᵢⱼ⁽ᵏ⁾ sᵢⱼ⁽ᵏ⁾ / Σₖ αₖ mᵢⱼ⁽ᵏ⁾

s is a pair's score; α is a configurable signal weight; m is 1 only when that evidence is available. Missing evidence is masked, not treated as a zero relationship.

Phase outputs and decision gates

Analysis

Evidence bundle

Normalized classes, role/anchor candidates, typed pairwise relationships, coverage, and source provenance. Include explicit unavailable-signal metadata.

Graph

Weighted graph and communities

Class nodes, cohesion edge weights, separate directed dependency records, Louvain community IDs, and clustering parameters.

Domain review

Candidate domain map

Community members, anchors, data ownership evidence, confidence, ambiguous/shared classes, and reasons to keep anchors together or separate.

Modularization

Module ownership map

Approved class and data ownership, module APIs, unresolved dependency violations, cross-module transactions, and focused validation results.

Contract design

Boundary dependency inventory

Consumer/provider, operation, source evidence, data exchanged, and proposed in-process API, HTTP API, event, or read-model pattern.

Extraction gate

Readiness and migration plan

Independent build/test/deploy readiness, data migration, observability, failure handling, rollout, rollback, and extraction order.

Proposed architecture workflow for planning and implementation. It intentionally separates domain discovery from microservice deployment and keeps uncertain boundaries visible for review.
